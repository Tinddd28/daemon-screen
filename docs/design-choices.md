# Выбор технологий и нюансы: три шага конвейера

Захват экрана распадается на **три независимых шага**. На каждом свой выбор
технологии, и эти выборы **ортогональны** — менять один можно, не трогая другие.
Частая путаница — считать их альтернативами друг другу (например «OpenGL вместо
libpng»); на деле это разные шаги, и нужны все три.

```
   ШАГ 1: получить буфер        ШАГ 2: распаковать в пиксели       ШАГ 3: закодировать
   ──────────────────────       ────────────────────────────       ───────────────────
   DRM/KMS  →  dma-buf fd   →    GPU: detile + convert → RGBA  →    RGBA → файл/поток
   (+ layout: pitch/offset/           EGL + OpenGL ES                    libpng (.png)
    format/modifier)            ИЛИ  Vulkan (один API)             ИЛИ  jpeg / видео-кодек
                               ИЛИ  mmap (только линейный буфер)
```

Что используется **сейчас**: `KMS (GetFB2 + PRIME)` → `EGL + OpenGL ES 2.0` →
`libpng` / `libjpeg-turbo` (выбор флагом `-f=png|jpg`).

---

## Шаг 1 — Получить буфер (DRM/KMS)

**Что на выходе:** не пиксели, а **dma-buf fd** (ссылка на GPU-память) плюс
раскладка — `width/height/format/pitch/offset/modifier`. См.
[drm-kms.md](drm-kms.md).

**Сейчас:** card-нода → `drmModeGetFB2` → `drmPrimeHandleToFD`. Требует
**root / `CAP_SYS_ADMIN`** (иначе ядро обнуляет GEM-хендлы — см.
[mistakes.md](mistakes.md) §A.1).

**Что можно заменить:**

| Вариант | Права | Согласие юзера | Фоновый режим | Когда |
|---|---|---|---|---|
| **KMS + `CAP_SYS_ADMIN`** (текущий) | root/caps | не нужно | да | тихий демон (DLP) |
| xdg-desktop-portal + PipeWire | не нужны | **нужно** (диалог) | нет | интерактивный инструмент |
| DRM master из TTY | master | — | нет | только на голом VT |

Нюанс: `CAP_SYS_ADMIN` — это **не** `drmSetMaster`; master отбирать у
композитора не надо (сломает вывод). Подробнее — [correct-approach.md](correct-approach.md) §1.

---

## Шаг 2 — Распаковать буфер в пиксели (GPU)

**Что на выходе:** линейный **RGBA8** в памяти. Нужен, потому что кадр обычно
**тайленый/сжатый** (AMD DCC) и в нестандартном формате (XR30) — построчно не
читается. GPU делает **detile + конвертацию формата**.

**Сейчас:** **EGL + OpenGL ES 2.0** (см. [egl.md](egl.md)). Внутри этого шага две
подроли:

- **EGL** — платформенный «клей»: контекст, конфиг, **импорт dma-buf** как
  `EGLImage`. Сам не рисует.
- **OpenGL ES** — собственно рендер: `samplerExternalOES` → рисование quad в
  RGBA8 FBO → `glReadPixels`.

**Что можно заменить — на двух осях (они независимы):**

*Ось A — платформенный слой (что поднимает GPU-контекст и импортирует буфер):*

| Вариант | Где применим |
|---|---|
| **EGL** (текущий) | headless на DRM/GBM — практически безальтернативен |
| GLX | только под X11 |
| WGL | только Windows |

*Ось B — рендер (что реально распаковывает):*

| Вариант | Замечания |
|---|---|
| **OpenGL ES 2.0** (текущий) | минимум кода; требует EGL, чтобы вообще подняться |
| десктопный OpenGL | то же, чуть другой профиль |
| **Vulkan** | самодостаточен — **заменяет EGL + рендер разом** (см. ниже) |
| `mmap` (без GPU) | **только линейный буфер**; на тайленом DCC не работает |

### Нюанс: Vulkan заменяет EGL + отрисовку одним API

Vulkan не нуждается в EGL: работает **headless нативно**, сам импортирует dma-buf
(`VK_EXT_external_memory_dma_buf` + `VK_KHR_external_memory_fd`), сам понимает
тайлинг (`VK_EXT_image_drm_format_modifier`), сам распаковывает (blit/compute в
линейный образ → `vkMapMemory`). То есть один Vulkan = то, что здесь делают
`EGL + OpenGL ES` вдвоём.

Цена: **заметно больше boilerplate** (instance/device/queue/command buffers/
барьеры/синхронизация). Для распаковки одного кадра — оверинжиниринг; оправдан,
если дальше и так строится Vulkan-пайплайн (кодек/обработка на GPU). Поэтому для
PoC выбран EGL+GLES2 — тот же результат, в разы меньше кода.

### Нюанс: почему `EGL_TEXTURE_EXTERNAL_OES`, а не `GL_TEXTURE_2D`

Источник тайленый/не-RGB — корректен внешний сэмплер (`samplerExternalOES`); с
обычной 2D-текстурой DCC-буфер часто не импортируется. Плюс обязательно
передавать **modifier** — иначе GPU не знает про тайлинг. (Это и был один из
блокеров ветки `OpenGL_part`, см. [mistakes.md](mistakes.md) §I.)

## Шаг 3 — Закодировать в файл/поток

**Что на выходе:** файл или сетевой поток. GPU-шаг отдаёт **сырые байты**, а не
готовый формат, — этот шаг превращает их в PNG/JPEG/видео.

**Сейчас:** доступны два энкодера, выбор флагом `-f=png|jpg`:
- **libpng** → `.png` (`ds_save_png`) — по умолчанию, без потерь, с альфой;
- **libjpeg-turbo** → `.jpg` (`ds_save_jpeg`) — с потерями (`quality`), альфа
  отбрасывается (через `JCS_EXT_RGBA` RGBA скармливается напрямую).

**Ключевой момент:** этот шаг нужен **всегда**, независимо от выбора на шаге 2.
Ни OpenGL, ни Vulkan не отдают PNG/JPEG — только пиксели. «Использовать OpenGL
вместо png/jpeg-библиотеки» невозможно: это разные шаги.

**Что можно заменить:**

| Вариант | Когда |
|---|---|
| **libpng** (`-f=png`, дефолт) | скриншот без потерь; резкий текст/UI |
| **libjpeg-turbo** (`-f=jpg`) | компактный кадр с потерями; фото-содержимое |
| raw PPM/BMP | отладка, ноль зависимостей |
| видео-кодек (VAAPI/NVENC/x264) | стрим по сети (кадры, не файлы) |

Нюанс JPEG: на резких краях и тексте (а их на экране много) появляются блочность
и «звон» — для скриншотов PNG обычно предпочтительнее; JPEG выигрывает на
фотографическом содержимом и когда важен управляемый через `quality` размер.

Для целевого сценария (демон, отправка по сети) именно здесь PNG заменяется на
видео-кодек; PNG остаётся как debug-выход. См. [correct-approach.md](correct-approach.md) §6.

## Сводка: ортогональность выборов

| Шаг | Задача | Сейчас | Главная альтернатива | libpng причём? |
|---|---|---|---|---|
| 1 | достать буфер | KMS + `CAP_SYS_ADMIN` | portal + PipeWire | — |
| 2 | распаковать в пиксели | EGL + OpenGL ES | Vulkan (один API) / `mmap` (линейный) | — |
| 3 | закодировать | libpng / libjpeg (`-f=png\|jpg`) | видео-кодек | **это и есть шаг 3** |

Реальные развилки: на шаге 2 — «EGL+GLES **или** Vulkan **или** (для линейного)
`mmap`»; на шаге 3 — «PNG **или** кодек». Шаги **не** конкурируют между собой —
их проходят по очереди все три.
